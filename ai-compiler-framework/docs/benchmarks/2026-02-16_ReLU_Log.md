# 🚀 ReLU 커널 벤치마크 (Instruction Bottleneck 분석)

- **작성일:** 2026-02-16
- **디바이스:** NVIDIA RTX 3060
- **커널 타겟:** relu_f32_naive, relu_f16_vec2_half2

---

## 1️⃣ 성능 요약 (유효 대역폭)

> Purpose: Activation Function (Y = max(X, 0))  
> Pattern: Read(X) + Write(Y) → 2-way traffic  
> 유효 대역폭 정의: (bytes(read) + bytes(write)) / time

| 커널 버전 | 데이터 타입 | 입력 크기 | 실행 시간 | 유효 대역폭 (GB/s) | 효율(vs Copy F32) | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| F32 Naive | F32 | 4096² (16M) | 0.465 ms | 288.88 | 97% | ✅ |
| F16 Naive | F16 | 4096² (16M) | 0.274 ms | 244.82 | 82% | ⚠️ |
| F16 Vec2 | F16 | 4096² (16M) | 0.241 ms | 277.99 | 93% | ✅ |

---

## 2️⃣ 심층 분석: F16 Naive가 느린 이유

### 📉 명령 발행(Instruction Issue) 병목
- ReLU는 연산이 매우 단순해, 성능은 대부분 “데이터를 얼마나 빨리 옮기느냐”에 의해 결정된다.
- 하지만 F16을 스칼라로 처리하면(half 단위),
  벡터화(half2) 대비 **명령 발행/파이프 효율이 낮아져** 메모리 파이프를 끝까지 포화시키지 못할 수 있다.
- 그 결과 F16 Naive는 약 245 GB/s에서 멈추며, Copy baseline 대비 효율이 82% 수준으로 떨어진다.

### 🚀 half2(Vec2) 벡터화 효과
- half2는 2개의 half를 32-bit로 묶어 처리한다.
- 효과:
  - 로드/스토어 요청 수 감소
  - 연산도 __hmax2 형태로 묶여 처리 가능
- 결과적으로 병목이 완화되며 244.8 → 278.0 GB/s로 약 +13% 개선된다.

---

## 3️⃣ 결론
- F32는 Copy baseline 대비 97%로 매우 우수하다.
- F16에서는 half2 벡터화가 사실상 필수이며,
  벡터화 적용 후에는 93% 수준까지 효율이 회복된다.
