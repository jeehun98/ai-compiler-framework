# 🚀 Element-wise Add 커널 최적화 로그

- **작성일:** 2026-02-16
- **디바이스:** NVIDIA RTX 3060
- **커널 타겟:** `add_f16_vec2_half2` / `add_f32_naive`

---

## 1️⃣ 성능 요약 (유효 메모리 대역폭)

> **Note:** Add 연산은 전형적인 **Memory Bound** 커널이므로 핵심 지표를  
> **유효 대역폭(GB/s)** 로 측정함.  
> (RTX 3060의 이론적 메모리 대역폭은 모델/메모리 구성에 따라 다르며, 대략 수백 GB/s 범위)

| 커널 버전 | 데이터 타입 | 입력 크기 | 실행 시간 (Latency) | 대역폭 (Bandwidth) | 비고 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **F32 Baseline** | F32 | 4096² | 0.640 ms | **314.66 GB/s** | **대역폭 포화에 근접** |
| **F16 Naive** | F16 | 16.7M (1D) | 0.343 ms | 293.59 GB/s | 명령 발행/요청 오버헤드로 효율 손실 |
| **F16 Vec2** | F16 | 4096² | **0.325 ms** | **310.08 GB/s** | **Naive 대비 효율 회복 (+5.6%)** |

## 2️⃣ NCU 프로파일링 분석 (근거)

Nsight Compute로 측정한 결과, 이 커널이 **DRAM 대역폭을 높은 비율로 사용**하고 있음을 확인함.

### 📊 주요 지표 (F32 기준)

- **Memory Throughput:** **93.82%**
  - **의미:** 측정된 구간에서 DRAM 대역폭 활용률이 매우 높음.
  - **해석:** 병목이 연산(SM)이 아니라 **메모리 이동**에 있음을 강하게 시사함.

- **Compute Throughput:** **18.68%**
  - **의미:** 연산 유닛은 상대적으로 여유가 있음.
  - **해석:** Add는 (대략) 1 read + 1 read + 1 write 대비 연산이 1회로, 본질적으로 연산 집약도가 낮아 정상적인 패턴임.

- **Grid 구성**
  - `Grid: 65536, Block: 256`
  - **해석:** 전체 SM을 포화시키기에 충분한 워크로드 크기를 생성함.

## 3️⃣ 이슈 분석 — Memory Bound 특성

### 🔎 F32 vs F16: 대역폭과 실행 시간 관계

- **관찰:** 유효 대역폭(GB/s)은 F32(314.66)가 F16 Vec2(310.08)보다 약간 높지만,  
  **실행 시간은 F16이 약 2배 빠름 (0.640ms vs 0.325ms).**

- **원인(핵심):**
  1. **총 데이터 이동량**이 병목인 커널에서, F16은 요소당 바이트 수가 절반이라 **이동해야 할 총 바이트가 감소**함.
  2. F32가 약간 더 높은 GB/s를 보일 수는 있지만, **절대 데이터량(바이트)** 측면에서 F16이 유리해 총 시간은 더 짧아질 수 있음.

- **교훈:** Memory Bound 커널에서는 **데이터 타입 축소(예: FP16)** 가 곧 실행 시간 단축으로 직결되는 경우가 많음.

### 🔎 Naive vs Vec2: 벡터화의 필요성

- **Naive (293.59 GB/s):** `half` 단위로 처리하면 로드/스토어 및 관련 명령 발행이 늘어 **요청 오버헤드**가 커질 수 있음.
- **Vec2 (310.08 GB/s):** `half2`로 벡터화하면 유효 요청 횟수가 줄어, 메모리 파이프라인 활용률이 개선됨.

## 4️⃣ 커널 구현 전략

### ✅ v1.0: Naive 구현
- 단순 `idx` 기반 루프 구조.
- 홀수 크기(Odd shape) 입력을 안전하게 처리하는 Fallback 경로 포함.

### ✅ v2.0: 명시적 벡터화 (`__half2`)
- **적용 조건(예시):**
  - 원소 개수가 짝수
  - 포인터 정렬이 `half2` 접근에 적합(최소 4바이트 정렬)
- **구현:**
  - `reinterpret_cast<const half2*>` / `reinterpret_cast<half2*>`
  - `__hadd2` 인트린직 사용
- **효과:**
  - 메모리 요청/명령 발행 오버헤드 감소
  - 유효 대역폭 회복 → 포화 수준에 근접

---

## 5️⃣ 결론

> **Memory Bound 커널의 핵심은 “연산 최적화”가 아니라 “대역폭을 채우는 것”**

1. **높은 대역폭 활용:** Memory Throughput **93.82%**는 병목이 DRAM이며 활용률이 매우 높음을 보여줌.
2. **FP16의 실전 효용:** 데이터 이동량 감소로 실행 시간이 크게 단축될 수 있음.
3. **벡터화는 마무리:** FP16만으로 부족한 효율은 `half2` 벡터화로 추가 회복 가능.
